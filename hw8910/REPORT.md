## 3. Граф, результаты и кеш

```text
prepare_task → artifact_task → gate_task ── FAIL → отказ, прежний accepted
                                  └─ PASS → publication_task → accepted + journal
```

Подготовка проверяет вход (для .real — JSONL-схему и уникальные id), считает хеш,
число строк и сохраняет маленький результат. На входе файл и config; на выходе
описание с SHA-256 и параметрами. Получение артефакта читает уже обученную модель и
проверяет её файлы. Gate читает связанный полный отчёт. Публикация не кешируется.
Ни веса, ни тензоры не пересылаются результатами задач.

`cache_key` = SHA-256 канонического JSON `{data_sha256, config}`. Одинаковые
байты в разных путях дают одинаковый ключ. Учитывается весь config, в частности
revision токенизатора, template_sha256, max_length, code_revision. У Prefect к
ключу добавлен хеш namespace рабочего каталога, чтобы не вернуть описание из
другого независимого стенда. Результаты Prefect persist_result=True сохраняются
в `.prefect/storage`; stdlib-совместимый кеш — в `<workspace>/cache`.

Попытка получает отдельный UUID в attempts.jsonl. Её id не входит в ключ результата.
Изменение только пути не означает изменение данных; новый attempt не требует
новой подготовки. Изменение содержимого или параметров подготовки требует.

## 5. Проверка допуска и публикация

`validate_release` проверяет schema_version именно int 1, непустые идентификаторы,
четыре lowercase SHA-256, канонический runtime, статус complete, passed именно True,
конечные числовые accuracy/format_rate в [0,1] без bool/строк и полное совпадение
идентичности manifest/report. До публикации и загрузки хешируются реальные файлы.
Модельный хеш — хеш закреплённого словаря относительный путь → хеш байтов файла;
у адаптера включены adapter_config и веса, у базы закреплена commit revision.

Полная обвязка дополнительно проверяет исходные файлы по SHA-256, пересчитывает
score из raw, behavioral и полный quality_gate ДЗ 6+7. Runtime закрепляет system,
do_sample, seed, max_new_tokens=32, enable_thinking=False, dtype, device, точные
пакеты, tokenizer/template и код backend. Изменение кода генерации требует нового
eval. Смена только обслуживания маршрутов не меняет саму генерацию.

Проверены неполный/чужой отчёт, отказ, NaN/Inf, неверные типы, устаревший runtime,
подмена raw и метрик, ошибка fsync и replace. Старый accepted при отказах сохранён.
SHA-256 реального указателя **до и после** отказа:

`8a83707b9c09dcdeaf9427df57ee084676a73c275aaca0399474a5dc56ecdaed`

Подтверждение: `evidence/real-release/release-decision.json` и verify-delivery.log.
Фикстуры examples/.lab имеют STUB ONLY и synthetic=True, не являются eval модели.

Публикация одного писателя: durable intent → временный файл рядом с target →
flush/fsync → os.replace → атомарно перезаписанный журнал с дедупликацией.
При падении после pointer намерение остаётся; повтор завершает журнал. При падении
после журнала повтор также не добавляет событие. Идентификатор выпуска хеширует
весь manifest и связанный report, учитывая runtime и evaluation_run_id. Это не
только model_id. Попытки допускаются многократно, события одного release — один раз.
Гарантия — для сбоев процесса; конкуренция писателей и внезапное отключение питания
с fsync каталогов в этот учебный контракт не входят. Принятый JSON не MLflow alias.

## 7. FastAPI и настоящий ответ

`create_app` принимает backend_factory. Shared ServiceState используется обоими
адаптерами; модель загружается один раз, manifest фиксируется при запуске.
В lifespan начинается загрузка, проверяются файлы, выполняется прогрев; ready=True
устанавливается только после успеха. До этого health=200, ready/generate=503.
Ошибка загрузки оставляет ready=False. Для real manifest случайный StubBackend
запрещён. `/debug` у FastAPI включён только для синтетического стенда.

Валидация JSON/prompt/лимита выполняется до backend. Тело до 64 KiB, prompt до
4096 символов; реальный backend проверяет до 512 входных токенов вместе с шаблоном
и system. Stub поддерживает 1..32, настоящий API — только оценённый лимит 32.
Нецелые, bool, строковые/нулевые/чрезмерные лимиты отклоняются 4xx. Вычисление
сериализовано lock. Отдельного ограничения длины очереди нет.

Реальный smoke: вопрос «Кто связывает данные с ViewHolder? A: Service; B: Dialog;
C: Adapter». Получен `{"answer":"C"}` (правильная метка C),
6 выходных токенов.
request_id: `c39f0a5d-1d67-42d6-b7c7-e7b87a01d02a`.
model_id: `Qwen/Qwen3-0.6B@c1899de289a04d12100db370d81485cdf75e47ca`.
runtime_sha256: `a6120cd0e7027050258a3a617ba726fbd11f5b8fc370e81c383cade7a2aed702`.

Длительности и второй ответ после перезапуска: `evidence/real-api/smoke.json`.
Неправильный лимит получил 422. Сырые логи серверов сохранены. Общие HTTP-тесты
сверяют число вызовов до/после каждого из четырёх неверных запросов.

Кандидат отклонён, поэтому удерживается исходная baseline. Её собственный
report-baseline.json НЕ помечен PASS: baseline тоже ошибается (включая 1/3
behavioral), это прежняя точка отсчёта, а не новый кандидат, прошедший допуск.
Bootstrap существующей базы отделён от publish_release. Пороги ради API не менялись.

## 8. Нагрузка и объяснение

После реального прогрева: первые 8 golden-вопросов, один и тот же порядок/состав
для concurrency=1 и 2, MPS, лимит 32, одинаковый runtime. Восемь запросов в каждом
режиме, не 8 суммарно. Все 16 строк, включая фактические output_tokens, model_id,
request_id, статусы и длительности: `evidence/real-api/benchmark/requests.jsonl`.
Инструмент сохраняет ошибки и таймауты, они не исчезают из n.

| concurrency | n | успех / ошибка | пакет, с | success req/s | mean latency, с | max latency, с | mean compute, с | mean queue, с |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 8 | 8 / 0 | 1.0512 | 7.610 | 0.1310 | 0.1472 | 0.1264 | 0.0000 |
| 2 | 8 | 8 / 0 | 1.0116 | 7.908 | 0.2375 | 0.2634 | 0.1257 | 0.1069 |

Ошибок в этом прогоне нет; их mean/max в summary.json — null, а не 0.
Рост задержки при двух клиентах объясняется очередью: compute почти неизменно,
второй запрос ждёт lock. Это последовательный Transformers backend без batching.
Разница throughput на столь маленьком n не доказывает ускорения.

Prefill обрабатывает входные токены и строит KV-cache; decode последовательно
вычисляет выходные токены, переиспользуя кеш ключей/значений attention. Его память
растёт с длиной последовательности, числом слоёв, размерностью и типом данных.
Длины входов/выходов влияют на длительность. Единственный JSON даёт только полную
задержку: TTFT, ITL и устойчивый p95 не измерены. Скорость SGLang/vLLM, их управление
KV-cache и планирование batch этим сервисом не измеряются.

## 9. Версия, перезапуск и откат

`test_http_loaded_version_and_rollback`: старт на A → публикация B отдельным
процессом → ответ и metadata всё ещё A → перезапуск → B → восстановление ранее
принятого A + перезапуск → ответ и metadata A. Две STUB-версии — инженерный опыт,
не новая оценка качества. Собственный тест сбоя между pointer и journal запускает
три настоящих процесса: failed, complete, complete; journal содержит одно событие,
attempt_id три разных. Журналы сохраняют все шаги.

Отдельный real smoke дважды загрузил один принятый baseline manifest и подтвердил
модель и runtime ответом. Второй реально допущенной версии нет. План реального
отката: взять архивированный ранее принятый manifest с прежним полным допуском,
повторно проверить его файлы/отчёты, опубликовать и управляемо перезапустить API.
Само изменение accepted.json не означает перезагрузку памяти.

## 10. Доступ, ограничения и проверяемость

[README.txt](README.txt) содержит полные команды. Веса и окружения исключены из Git.
MLflow артефакт доступен через исходный run; точный base snapshot должен быть в HF
cache (или заранее восстановлен из копии). Для другой машины нужны исходные Docker
тома mlops-hw6 и snapshot. real_release восстанавливает URI под текущую машину.
Маленькие полные отчёты, raw и протокол включены в evidence; проверить без весов
и MLflow: `.venv/bin/python scripts/verify_delivery.py` (exit 0).
Проверка честного отказа: `scripts/check_gate.py --workspace .real` (exit 1).

Ограничения: учебная выборка 50+3, один runtime и одно устройство, единичный замер
8+8, без устойчивого p95, без streaming/TTFT/ITL, без сравнения движков и замера
долгой нагрузки. Отдельно не измерялись загрузка/пиковая память сервиса; в benchmark
загрузка и warmup исключены. Очередь без явного bound. Исходная база даёт ошибочные
in-domain отказы; один успешный smoke не устраняет эти известные ошибки. Разметка
golden унаследована из HW67 с пометкой об обязательном человеческом просмотре;
человеческая проверка не имитируется. В некоторых логах завершения torch есть
resource_tracker warning о semaphore; HTTP-запросы и управляемые рестарты успешны,
длительное исследование этого предупреждения не проводилось.
