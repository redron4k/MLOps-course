5. Методика измерений и Prometheus

Монотонные часы на каждом клиенте: time.perf_counter(). TTFC = время первого содержательного JSON chunk − фактическая отправка; duration = конец чтения − отправка; inter-chunk latency = разности времён прихода соседних содержательных частей. Маркер done не является частью ответа. При N=1 массив интервалов пуст и среднее отсутствует. Метрики TTFT, TPOT и tokens/s не заявляются: фактических токенов LLM здесь нет. Для возможного реального backend: TTFT до первого содержательного токена, TPOT=(t_last−t_first)/(N−1), при одном токене TPOT=null; счётчик должен использовать tokenizer той же закреплённой модели.

В каждой строке сохранены schedule, sent, first, end, статус, outcome, Pod, фактическая версия, request ID, количество частей, интервалы и лаг отправки. Успех требует HTTP 200, done и ожидаемое количество частей. 429/503 — отклонённые, поток без done — interrupted, дедлайн клиента — timed_out. «Просроченные» здесь определены истечением timeout=35 с; лаг отправки считается отдельно и не включается в TTFC. Таблица содержит N, p50/p95 только успешных ответов, доли ошибок/тайм-аутов; завершённость не выводится из одного HTTP-статуса.

6. Собственные проверки, ограничения и ревью

Девять HTTP/контрактных тестов: прогрев/probes, изоляция диалогов, ограничение очереди с учётом отказов, оборванный поток/освобождение слота, повреждённый артефакт идентичность расписания с долей 80% воспроизведение исходного дефекта probes классификация HTTP 500 с текстовым телом и продолжение обслуживания старых сетевых соединений при снятой readiness во время preStop. Исходная запись аварийного bridge HTTP 500 сохранена со старым outcome=connection_error и фактическим status=500; это ошибка классификации клиента, устранённая регрессионным тестом. Она не влияет на долю неуспехов и не относится к штатному rollout. Kubernetes-проверки в run_lab дополнительно отправляют HTTP-запросы при прогреве, после отката, при SIGKILL и после замены Pod, проверяют версии и две контрольные строки. Строгий gate сдачи проверяет сырые доказательства, 12 полных сравнений, последовательности алертов и четыре графика; ненулевой exit означает незавершённый пункт.

Сохранён также первоначальный сбой Docker Desktop и ошибка разработки метаданных; они не выдаются за поведение исправленного приложения. Воспроизводимые итоговые измерения должны быть получены при доступном Docker и Kubernetes. Один узел kind не доказывает отказоустойчивость к потере узла, сеть другого CNI, производительность GPU, настоящий KV-cache, batching и порядок токенов. Клиентская история тестирует переносимость/изоляцию контекста, но не является проверкой качества ответов модели.

Ревью PR: закрепление диалога

# Ревью PR: закрепление диалога за Pod

**Решение: направить новый запрос на B.** A начнёт работу через 3 с даже с готовым
префиксом, свободная B пересчитает контекст за 0,8 с: ожидаемый выигрыш — 2,2 с.
История диалога должна находиться в запросе или внешнем хранилище. Локальность
кеша — преимущество при выборе реплики, а не причина бесконечно ждать очередь.
В нашем стенде снимаем ClientIP и повторяем тот же сценарий через обычный
Service. Небольшой набор префиксов помещается в кеш обеих реплик; для настоящего
KV-кеша стоимость дублирования потребует отдельной проверки.

Перед допуском запроса проверяем свободный слот, лимит очереди, запас памяти/KV
и дедлайн. Если ни одна реплика не укладывается в бюджет, возвращаем явный
отказ; повторы считаем отдельными попытками. Для более точного выбора нужны
p50/p95 очереди и prefill по длинам входа, hit/miss, активные потоки, batching,
CPU/GPU и KV-память, стоимость передачи контекста и свежесть сигналов. Политика
сравнивает прогноз `queue + uncached prefill + network` и снимает affinity при
превышении ограниченного выигрыша от кеша. Средняя CPU этого сравнения не заменяет.

При потере A восстанавливаем историю на B, проверяем фактическую версию модели
и пересчитываем префикс. Уже начатый поток оставляем на A до завершения в grace
period. Аварийный обрыв явно фиксируем; повтор имеет новый attempt ID. Части
двух генераций нельзя склеивать без протокола продолжения и дедупликации.

Связанный кейс — авторы Google в llm-d: cache affinity действует до предела
насыщения, затем выбирается менее загруженная реплика. Первичный источник:
[Sticky Until Saturated: Token-Aware Routing in llm-d, 17.08.2026](https://llm-d.ai/blog/sticky-until-saturated-token-aware-routing).
Их GPU-результаты на CPU-имитатор не переносим. Сам материал лекции отсутствует,
поэтому совпадение кейса с разобранным на лекции не подтверждено.
